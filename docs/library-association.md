# 本地作品与目录作品的关联

媒体库里的每个作品分组（`clusterKey`）可以由用户手动指定对应 animego 目录里的哪部作品。自动匹配（文件名 + 16MB hash）会认错，而认错之后弹幕与「看完」的进度都会落到别的作品上；关联让用户说了算。

关联按作品分组记，不按文件夹记。`clusterKey` 由共享解析语料算出，语料更新或目录改名都可能让它变化，所以每条关联同时记下当时的成员文件（最多 64 个）。

## 接口

`PUT /api/library/association`，请求体三选一：

| 请求 | 含义 |
| --- | --- |
| `{"clusterKey":"…","mode":"manual","anilistId":154587}` | 认定为这部目录作品。标题与封面由服务端从目录详情读取（与 `GET /api/anime/{id}` 共用十分钟缓存），不接收客户端提供的值 |
| `{"clusterKey":"…","mode":"none"}` | 不是目录里的作品（自己录的视频、找不到条目的冷门番） |
| `{"clusterKey":"…","mode":"auto"}` | 删除关联，回到自动匹配 |

响应 `{ association }`。`association` 是 `{mode, anilistId?, title?, setAt, syncedElsewhere?}`，`auto` 时为 `null`。

`syncedElsewhere` 是 `[{anilistId, title, episodes[]}]`：这个分组里已经看完、并且已经回写到**别的**作品的集，按作品归拢。nagare 不会自动撤销这些记录，界面据此引导用户去那部作品的页面自己改进度。这份清单存在关联记录里，多次改关联会累积；改成认定为清单里的某部作品时，那部作品的条目会去掉（回写到它上面的就不算写错了）；回到自动匹配时随关联一起删除（界面在清单非空时先确认）。

`POST /api/library/association/dismiss-synced {clusterKey, anilistId}` 去掉清单里某部作品的那一条（用户改完那部作品的进度之后点「已处理」），响应同样是 `{ association }`；分组没有关联时 409。

| 状态码 | 情况 |
| --- | --- |
| 400 | 缺少或过长的 `clusterKey`、`mode` 未知、作品 ID 不合法 |
| 409 | 当前扫描结果里没有这个分组（刷新后重试）；或正在播放这个分组里的某一集（停止播放后再改） |
| 503 | 目录不可用 |

读取目录详情失败时，按 animego 的错误类型映射状态码。分组已经不在库里（盘没插、目录删了）时，只要库里还存着它的关联，`auto` 仍然可以把关联删掉。对从没关联过的分组发 `auto` 什么都不改（它本来就在自动匹配），不会为一次重复点击清掉它的匹配缓存。

从读分组成员、检查播放状态到落盘，与媒体库重扫串行执行，中间不会插进一次重扫；这把锁在读取目录详情之后才拿，网络慢不会卡住重扫。

上游字段落盘前会先清理：封面地址必须在图片白名单里（与目录图片相同：https、无 userinfo、AniList / TVDB 图床或配置的元数据站点），且不超过 2KB，否则不保存封面；标题截到 200 字。

## 改关联时作废哪些匹配

`bindings` 是「文件 → 自动匹配结果」的缓存。改关联时，在同一次落盘里作废分组内与新关联不一致的缓存：

- 认定为作品 X：只作废指向其他作品的匹配，已经匹配到 X 的照用，弹幕与集号不必重新查。
- 标为 none 或回到自动匹配：分组内的匹配全部作废。

被作废的那几集会清掉「已回写」标记。进度本身不动，重看这一集并看完时，进度会按新关联写到正确的作品上。落盘失败时，内存里的改动整体回滚。

播放结束时的「看完」回写，在请求前后各核对一次这一集的匹配是否还是开播时那一条：用户点了停止、回写还没完成时改了关联，就不再按旧匹配写到旧作品上；请求途中被改，这一集不标记为已回写，留到重看时按新关联再写。

## 媒体库视图

`GET /api/library` 的每个分组多一个 `association` 字段（没有关联时省略）。没有关联的分组另带 `matched: {anilistId, title}`：簇内匹配最多的那部作品（只让正片投票，没有正片匹配过才看全部；平票取 ID 小的），还没认出来时省略，界面据此显示「自动匹配到 X，还没确认」并可一键确认。每个文件多一个 `group`（文件名里的字幕组），同一集有多个版本时界面靠它区分。同一个 `clusterKey` 出现在多个库目录里（同一部番分在两块盘上）时，视图把它们并成一个分组，两边一模一样的副本（同名、同大小、同修改时间）只算一份。放送表的 `inLibrary` 也把手动认定的作品算在内。认定为作品时，分组封面和「继续观看」卡片改用那部作品的标题与封面，封面地址是 `/art/<cap>/assoc/<clusterKey>?v=<作品 ID>-<设定时间>`：客户端只拿到键，图床地址只保存在服务端。封面响应按 immutable 缓存，所以地址里带版本，改认成别的作品就是新地址；自动匹配来的封面地址同样带上匹配时间。标为 none 的分组不显示任何作品封面。

## 扫描后自动识别作品

移植自 animego「我的库」导入时的匹配（`importPipeline.js` 的 processCluster）。每次扫描完成后，后台给每个还没认出作品、也没被用户认定过（含标为 none）的分组挑候选文件，算首 16MB 指纹，连同文件名、大小、集号和文件名里的标题交给 `POST /api/dandanplay/match`——与播放前的匹配是同一份请求。认出来的结果落成那个文件的匹配缓存（`bindings`），所以封面、`matched`、按作品归组都走现有的路径，播放这个文件时也直接用它。实现在 `internal/api/identify.go`。

- **挑哪个文件**：正片（或剧场版）里集号最小的；已经匹配过作品、只缺封面的（早期版本存下的匹配）排最前。分组里一个带集号的都没有时（剧场版、单个特别篇），拿一个没有集号的文件按第 1 集问，**只记作品与封面**：没有集号的文件播放时本来就不匹配弹幕、不回写进度，识别不给它开新的回写路径。
- **预算**：一个分组一周之内最多问两个文件。按「这一周问过几个文件」算，不是每一轮两个——上游没有的番不会被一轮两集地问完整季。同一部番一模一样地拷在两块盘上（同一个 fileId）只算一个文件。
- **什么时候不读**：最近两分钟内还在被写入的文件先跳过（BT 乱序写入，首 16MB 可能还是空洞），静默期过了自动再来一轮。读之前再 stat 一次：大小或修改时间与扫描时不一致就这一轮跳过，不把错的指纹缓存在仍然有效的 fileId 下。修改时间在未来的（exFAT 时区、时钟漂移）当作已经静置。
- **限速与暂停**：两次请求之间隔 1.1 秒（animego 按 IP 限速 1 req/s）。网络失败、5xx、限速（429），以及 403 / 404 / 410 这类「接口整体不让用」的 4xx：整轮暂停（限速 2 分钟，其余 5 分钟），什么都不记；暂停期内的重扫 kick 不提前打断暂停。400 / 413 / 422 是这一次请求的内容不对：按「问过没认出」记，接着试下一个文件。响应解析不了（多半是那一部作品的数据有问题）：只推迟那一个文件一小时，排在后面的分组照常识别；连续三个文件都这样才整轮暂停。读不了的文件同样只推迟一小时（日志只记一次）。
- **问过的记录**：`state.json` 的 `identifyAttempts`（fileId → 时间），凡是得到确定答复（认出来、上游没有、请求被拒、认出了却没落盘）都记，一周之内不再问同一个文件；过期的按时间清，不按文件在不在——外接盘拔掉的那一轮扫不到它的文件，插回来不用从头问。指纹随同一次写入缓存。这份记录是纯缓存，不进 `schemaVersion`。
- **算认出来了**：分组里有正片（或剧场版）的匹配指向某部作品，并且有封面，或这一周已经问过（上游没有封面、或已有一条指向别的作品的旧匹配，再问答案也一样）。认出了番剧却没有作品 ID 的（上游没对应上）照样保存封面，但按「问过没认出」扣预算。
- **不覆盖**：核对与写入在 store 的同一把锁里（`SaveIdentified`）：分组有关联的不写；文件已经有一条指向【别的】作品的匹配（播放时匹配到的）不改；指向同一部作品时只补它缺的封面、标题、弹幕集。写之前还按文件再查一次关联（重扫可能把关联迁到了新键上）。上游给的标题、封面地址落盘前有长度上限。
- **进度**：`GET /api/library` 在识别进行中、重扫后已排上队、或上一轮暂停时带 `identify: {running, done, total, error?}`。重扫请求返回时进度已经是「排上队了」，界面重读就开始刷新（识别中每 3 秒，暂停时每 30 秒，标签页不可见时不刷新）；只有媒体库页轮询，别的页面不拉。

与决议 P1（扫描懒算 hash）的关系：P1 挡的是「导入一千集要读 16GB」（逐文件全量算指纹）。这里每个分组一周之内最多读两个文件的首 16MB，量级是「分组数 × 16MB」，在后台限速进行；逐文件的指纹仍然延到首次播放前。2026-10-08 用一份真实媒体库（339 个视频、37 个分组）实测：只发文件名关键词能认出 21 个，其中 2 个认错季；带指纹 37 个全部认对，用时约一分钟。

## 重新扫描后跟上分组变化

重扫是串行执行的。每次扫描之后：

- 键还在：把成员更新为分组当前的文件。
- 键不见了：在还没有关联的分组里，找一个与旧成员**两边都超过一半**重合的分组，把关联迁过去。只看旧成员这一边不够：第一季、第二季被合进同一个分组时，第一季的关联会盖住第二季。旧成员只记了前 64 个，所以新分组那一边分两步看：抽样的成员里过半，并且新分组的文件数少于旧分组总文件数（`memberCount`）的两倍。同时有多个配对成立时，重合多的先配。
- 都找不到：保留原样。多半是外接盘没插上，或这个目录这次扫描失败，盘接回来键就又对上了。

已知的限制：

- 键变化的同一次扫描里，分组的文件数又翻了一倍以上时，不会自动迁移，需要重新指定一次。
- 回到自动匹配会连同「已回写到别的作品」的清单一起删除，界面在清单非空时应先确认。
- 一个分组里混了两部作品（文件名解析成同一个标题）时，目前不能拆开，只能整组关联。

## 状态文件

关联存在 `state.json` 的 `associations` 字段里，文件格式升到 `schemaVersion: 2`。文件版本与程序不同时（升级或降级），第一次打开会先写一份备份 `state.json.v<原版本>.bak`：

- 权限 0600，先写临时文件并刷盘再改名，断电时不会留下半截备份；
- 去掉了 animego 会话凭证，重新登录即可；
- 已有一份可用的备份（普通文件、完整 JSON）就不覆盖；空文件或半截内容会被重写；
- 备份写不出来就拒绝启动，不在没有退路的情况下改写用户状态。

旧版本 nagare 读新文件时会忽略 `associations`，下一次写入时这个字段会丢失。

## 播放时

播放器经 `player.Options.Association` 按文件查它所在分组的关联。查的是分组索引，不是关联记下的成员，所以长篇第 64 集以后的文件同样查得到。不在媒体库里的源（磁力、在线候选）没有关联，照旧自动匹配。

- **认定为作品 X**
  - 缓存的匹配只有指向 X、且集号与文件当前的解析一致时才沿用；旧数据里集号缺失的就地补上，集号变了（共享语料更新）就重新匹配，免得弹幕和进度对不上同一集。
  - 重新匹配时先用 X 的标题（文件名里的标题正是认错的来源），再用文件名标题；结果必须是 X。
  - 弹幕匹配不上（或 animego 暂不可达）时，仍落一条只有作品与集号的匹配，看完照样回写到 X。弹幕状态里注明「看完仍会记到 X」（只在已登录、确实会回写时才说）。兜底没变化时沿用上一次的，不重写状态文件。
  - 以下情况不回写：集号认不出来（不猜第 1 集）；animego 认出了 X 却说没有这一集。跨季连续编号的集号在回写时换算，见下一节。
  - 特典、OVA、剧场版、NCOP/NCED、PV、CM、菜单、访谈、解说这类附加内容（`library.ParseEpisodeKind` 的分类）不匹配弹幕，也不回写，免得拿正片第 N 集的弹幕配它、或把它记成第 N 集。`bonus` 照常处理：BD 的「Disc 2 - 03」这类正片也会被归进去。
- **标为 none**：不匹配、不拉弹幕、不回写，缓存里的旧匹配也不用。
- **关联在播放期间被改**：后台匹配迟到的结果对不上新关联就不落盘；同一集重播时，落空的那次匹配不会用兜底盖掉另一次拿到的完整匹配；「看完」回写前后都会按当前关联再核对一次，对不上就不写、也不标记为已回写。
- **重扫**：关联迁到新键与换上新的文件索引在同一把锁里完成；按文件查关联时也持着这把锁的读锁，所以查到的键与关联一定来自同一次扫描。代价是重扫有关联需要更新时，落盘那几十毫秒里媒体库的读取要等一下。

媒体库视图里，认定过作品的分组只采用与认定作品一致的匹配（封面、集标题），不会借用迟到写回的、指向别处的那条。

## 看完回写的集号换算（跨季连续编号）

字幕组常常跨季连续编号：前作 28 集时，第二季的结局在文件名里叫 38。animego 账号记的是作品自己的集号（1 到总集数），而 nagare 回写用的逐集标记接口不检查总集数（animego#214），直接写 38 会被照单全收、进度变成 38。所以「看完」回写之前，先把文件里的集号换成作品集号。规则照 animego 网站自己的媒体库（`lib/library/episodeOffset.ts`）：

- 作品的总集数取自目录详情；偏移取自 animego 的 `GET /api/anime/{id}/episode-offset`（沿前作关系只累加 TV 正片）。偏移算不出来时是「未知」，绝不当 0 用。两样按作品缓存六小时，偏移一时取不到不缓存；开播匹配出作品后（已登录时）就在后台预取，看完回写时直接用缓存。
- 全有或全无：拿这个文件所在作品分组的**全部**正片集号（不含 OVA、SP 等）判断，每一集减去偏移都落在 1 到总集数里，才整组换算（单独一个 38，偏移 28 套得上，37 也套得上，所以不能只看这一集）。
- 连载中还没有总集数时：偏移已知、整组都排在偏移之后，同样按跨季编号换算。自己从 13 起编的分季文件也会被减掉 —— 那是记少，比记多好补。
- 套不上、组里又有集号超出总集数：
  - 偏移已知、这组跨过了偏移（前作与本季放在一个文件夹里，又认定为本季）：偏移之后的逐集换算，偏移之内的是前作，不记到这部作品上。
  - 组里有第 1 集（编号从 1 开始：一个文件夹装了两季、总集数登记少了、某个文件名被误读出一个大集号）：范围内的这一集照写，只拦超出的。
  - 没有第 1 集（第二季从 13 编起、只有一个结局 38）：**不回写**。宁可不记也不记错 —— 第二季的「13」其实是第 1 集，按 13 写会把整季标成看完。媒体库页的回写横幅说明原因，提醒确认是第几集后去 animego 网站手动标记、不要按文件里的编号标；偏移只是一时没查到的，提示重看这一集看完时会再试。
- 查不到总集数（animego 暂不可达），或总集数未知而偏移这次没查到：组里有第 1 集的照写，没有的先不写、重看时再试。
- 不在媒体库里的源（磁力、在线候选）只拿这一集判断。
- 实际写进账号的作品集号随进度一起记下（`progress.syncedEpisode`），改关联时列「之前记到别的作品上的集」用的就是它。

这套换算对认定过的作品和自动匹配的作品都生效。

## 界面

媒体库海报墙按作品归组（移植自 animego 的 dedupeSeries）：认定为同一部作品、或自动认出是同一部作品的分组（不同字幕组、不同文件夹）是一张海报，标「N 个版本」，集数按集号去重（同一部剧场版的几个版本算一集）；标题用作品名，封面取有封面的那个版本。两个分组的季数都从文件名里认出来了却不一样时不并在一起：多半有一个认错了季，单列一张标「待确认」的海报，点进去是它自己的作品页（在那里改对应作品）。认出了作品的海报进目录作品页（`/entry?id=<作品 ID>`），没认出的进这个分组自己的作品页。「在看 / 未开始 / 已看完」按集算：同一集的几个版本里看完任意一个就算看完这一集。打开媒体库页时距上次扫描超过两分钟会静默重扫一次（切回标签页时同样），新下载的集不用手点「重新扫描」。

作品页（`/anime/<clusterKey>`）的「对应作品」面板：显示认定的作品、自动匹配到的作品或「还没有对应的作品」，链到目录作品页；可以确认自动匹配、更换（选作品对话框按分组标题先搜一次，之后只在提交时搜）、标为不是目录里的作品、回到自动匹配。「之前记到别的作品」的集逐部列出，带去那部作品改进度的链接和「已处理」按钮。认定过作品后，媒体库海报与作品页标题改用作品名（作品页注明文件夹原名），媒体库搜索两种名字都能搜到。海报上的「待确认」只在归组置信度低、又没认过作品时出现。

目录作品页（`/entry?id=<作品 ID>`）的「本地媒体库」与 Discover 卡片上的播放按钮也以后端关联为准：

- 打开时按这个顺序代选本地作品：认定为这部作品的分组（连同自动认出是这部作品的分组一起）> 本机浏览器里的旧选择（以前记在 localStorage 的 `nagare:media-library:<作品 ID>`，分组在后端还没有别的决定时采用，并当场同步到后端、删掉旧记录；同步失败就先照旧用着，下次再试；这部作品已经认定了分组时旧记录直接作废）> 自动认出是这部作品的分组（只代选，不自动播放，也不自动认定）。
- 选中不止一个分组（比如 BD 版与网络版、几个字幕组各有几集）时合并成一张剧集表：每一集一张卡，主版本按「正在看的 > 看完的 > 认定过的版本 > 正片多的版本 > 分辨率高的」挑，同一集的其他版本以「字幕组（文件名里没有就用文件夹标题）· 分辨率」列在卡片下面（弹窗版的列表里也列），点了直接播放。播放哪个文件就认定哪个文件所在的分组。季数和认定过的版本对不上的自动认出分组不代选（多半认错了季），仍可在列表里手动挑。Discover 卡片的一键续播看的是下一集所在的分组认定过没有：认定过的版本旁边多了个自动认出的版本，不影响续播。「更换作品」回到列表，单独挑一个分组；列表里认出了作品的分组附上文件夹原名。
- 作品详情读不出来（离线、animego 不可用）时，页面列出媒体库里这部作品的本地分组，链到各自的作品页，本地播放不受影响。
- 在这部作品的页面上播放一个还没认定的本地分组，就是在确认它们是同一部：先认定、再播放（认定请求还没回来就关掉弹窗的，不再启动播放）。正在播放这个分组里的另一集时后端会拒绝认定，这时先停掉当前播放再认定一次 —— 反正马上要换成新的这一集。仍然失败不挡播放，但会说明这一集照旧按文件名自动匹配。
- 列表里没认过的本地分组会注明自动匹配到了哪部作品，同名文件夹分属不同季时据此挑对。
- 已经对应了别的作品、或标为不是目录作品的分组，在列表里显示它的状态，不能在这里直接选；要改去它的作品页改，免得在这里悄悄覆盖别处的决定。
- 选中的本地作品旁边有「在媒体库中打开」，链回 `/anime/<clusterKey>`。

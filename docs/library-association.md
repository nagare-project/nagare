# 本地作品与目录作品的关联

媒体库里的每个作品分组（`clusterKey`）可以由用户手动指定对应 animego 目录里的哪部作品。自动匹配（文件名 + 16MB hash）会认错，而认错之后弹幕与「看完」的进度都会落到别的作品上；关联让用户说了算。

关联按作品分组记，不按文件夹记。`clusterKey` 由共享解析语料算出，语料更新或目录改名都可能让它变化，所以每条关联同时记下当时的成员文件（最多 64 个）。

## 接口

`PUT /api/library/association`，请求体三选一：

| 请求 | 含义 |
| --- | --- |
| `{"clusterKey":"…","mode":"manual","anilistId":154587}` | 认定为这部目录作品。标题与封面由服务端从目录详情读取（与 `GET /api/anime/{id}` 共用十分钟缓存），不接收客户端提供的值 |
| `{"clusterKey":"…","mode":"none"}` | 不是目录里的作品（自己录的视频、找不到条目的冷门番） |
| `{"clusterKey":"…","mode":"auto"}` | 删除关联，回到自动匹配 |

响应 `{ association }`。`association` 是 `{mode, anilistId?, title?, setAt, syncedElsewhere?}`，`auto` 时为 `null`。

`syncedElsewhere` 是 `[{anilistId, title, episodes[]}]`：这个分组里已经看完、并且已经回写到**别的**作品的集，按作品归拢。nagare 不会自动撤销这些记录，界面据此引导用户去那部作品的页面自己改进度。这份清单存在关联记录里，多次改关联会累积；改成认定为清单里的某部作品时，那部作品的条目会去掉（回写到它上面的就不算写错了）；回到自动匹配时随关联一起删除。清除入口随界面一起做。

| 状态码 | 情况 |
| --- | --- |
| 400 | 缺少或过长的 `clusterKey`、`mode` 未知、作品 ID 不合法 |
| 409 | 当前扫描结果里没有这个分组（刷新后重试）；或正在播放这个分组里的某一集（停止播放后再改） |
| 503 | 目录不可用 |

读取目录详情失败时，按 animego 的错误类型映射状态码。分组已经不在库里（盘没插、目录删了）时，只要库里还存着它的关联，`auto` 仍然可以把关联删掉。对从没关联过的分组发 `auto` 什么都不改（它本来就在自动匹配），不会为一次重复点击清掉它的匹配缓存。

从读分组成员、检查播放状态到落盘，与媒体库重扫串行执行，中间不会插进一次重扫；这把锁在读取目录详情之后才拿，网络慢不会卡住重扫。

上游字段落盘前会先清理：封面地址必须在图片白名单里（与目录图片相同：https、无 userinfo、AniList / TVDB 图床或配置的元数据站点），且不超过 2KB，否则不保存封面；标题截到 200 字。

## 改关联时作废哪些匹配

`bindings` 是「文件 → 自动匹配结果」的缓存。改关联时，在同一次落盘里作废分组内与新关联不一致的缓存：

- 认定为作品 X：只作废指向其他作品的匹配，已经匹配到 X 的照用，弹幕与集号不必重新查。
- 标为 none 或回到自动匹配：分组内的匹配全部作废。

被作废的那几集会清掉「已回写」标记。进度本身不动，重看这一集并看完时，进度会按新关联写到正确的作品上。落盘失败时，内存里的改动整体回滚。

播放结束时的「看完」回写，在请求前后各核对一次这一集的匹配是否还是开播时那一条：用户点了停止、回写还没完成时改了关联，就不再按旧匹配写到旧作品上；请求途中被改，这一集不标记为已回写，留到重看时按新关联再写。

## 媒体库视图

`GET /api/library` 的每个分组多一个 `association` 字段（没有关联时省略）。放送表的 `inLibrary` 也把手动认定的作品算在内。认定为作品时，分组封面和「继续观看」卡片改用那部作品的标题与封面，封面地址是 `/art/<cap>/assoc/<clusterKey>?v=<作品 ID>-<设定时间>`：客户端只拿到键，图床地址只保存在服务端。封面响应按 immutable 缓存，所以地址里带版本，改认成别的作品就是新地址；自动匹配来的封面地址同样带上匹配时间。标为 none 的分组不显示任何作品封面。

## 重新扫描后跟上分组变化

重扫是串行执行的。每次扫描之后：

- 键还在：把成员更新为分组当前的文件。
- 键不见了：在还没有关联的分组里，找一个与旧成员**两边都超过一半**重合的分组，把关联迁过去。只看旧成员这一边不够：第一季、第二季被合进同一个分组时，第一季的关联会盖住第二季。旧成员只记了前 64 个，所以新分组那一边分两步看：抽样的成员里过半，并且新分组的文件数少于旧分组总文件数（`memberCount`）的两倍。同时有多个配对成立时，重合多的先配。
- 都找不到：保留原样。多半是外接盘没插上，或这个目录这次扫描失败，盘接回来键就又对上了。

已知的限制：

- 键变化的同一次扫描里，分组的文件数又翻了一倍以上时，不会自动迁移，需要重新指定一次。
- 回到自动匹配会连同「已回写到别的作品」的清单一起删除，界面在清单非空时应先确认。
- 一个分组里混了两部作品（文件名解析成同一个标题）时，目前不能拆开，只能整组关联。

## 状态文件

关联存在 `state.json` 的 `associations` 字段里，文件格式升到 `schemaVersion: 2`。文件版本与程序不同时（升级或降级），第一次打开会先写一份备份 `state.json.v<原版本>.bak`：

- 权限 0600，先写临时文件并刷盘再改名，断电时不会留下半截备份；
- 去掉了 animego 会话凭证，重新登录即可；
- 已有一份可用的备份（普通文件、完整 JSON）就不覆盖；空文件或半截内容会被重写；
- 备份写不出来就拒绝启动，不在没有退路的情况下改写用户状态。

旧版本 nagare 读新文件时会忽略 `associations`，下一次写入时这个字段会丢失。
